# Add Pyrefly to your IDE
Pyrefly seamlessly integrates into IDEs with our [VSCode](https://marketplace.visualstudio.com/items?itemName=meta.pyrefly) and [OpenVSX](https://open-vsx.org/extension/meta/pyrefly) extensions. For other editors like vim/emacs, see [other editors](#other-editors).

To see what features are supported by the IDE extension, see the [Supported Features page](../IDE-features).

## Quick start

1. Install the Pyrefly extension from the [VS Code Marketplace](https://marketplace.visualstudio.com/items?itemName=meta.pyrefly) or [Open VSX](https://open-vsx.org/extension/meta/pyrefly).
2. Open any Python file and the extension will activate automatically.

:::tip
Not seeing inlay hints in VS Code? Try setting `editor.inlayHints.enabled` to `true` in your VS Code settings.
:::

:::tip
Want the broader set of type-check diagnostics to show up in your editor by default? Run `pyrefly init`. It adds a `[tool.pyrefly]` section to an existing `pyproject.toml`, or creates a new `pyrefly.toml` if no `pyproject.toml` is present. You can also set `python.pyrefly.typeCheckingMode` to `"default"` or `"strict"` in your editor settings.
:::

## Customization

By default, Pyrefly should work in the IDE with no configuration necessary. But to ensure your project is set up properly, see [configurations](../configuration).

### VSCode Extension Settings

The following configuration options are IDE-specific and exposed as VSCode settings:

#### `python.pyrefly.typeCheckingMode`

**Type:** enum (`auto`, `off`, `basic`, `legacy`, `default`, `strict`, `all`) &nbsp; **Default:** `"auto"`

Controls how Pyrefly configures files not covered by a `pyrefly.toml` or `[tool.pyrefly]` section. Those configurations always take precedence over this setting. `auto` is a configuration-selection mode, not a preset.

- `auto` (default): searches for a nearby `mypy.ini` / `pyrightconfig.json` (or `[tool.mypy]` / `[tool.pyright]` in `pyproject.toml`) and migrates its settings in memory. If no migratable configuration is found, or migration fails, Pyrefly uses the `basic` preset. Nothing is written to disk.
- `off`: silences every error kind. Useful for editor users who only want IDE features (hover, go-to-def) without diagnostics.
- `basic`: minimal checking. Only high-confidence errors fire; everything else is silenced.
- `legacy`: looser preset for codebases migrating from mypy. Unlike `auto`, this is just the bare preset with no migration of any nearby mypy/pyright config.
- `default`: Pyrefly's default behavior.
- `strict`: additional error kinds on top of default for stricter checking.
- `all`: enables every error kind at error severity.

The non-`auto` values force a specific preset and skip configuration detection and migration.

#### `python.pyrefly.disableTypeErrors`

**Type:** boolean &nbsp; **Default:** `false`

Workspace kill switch for Pyrefly type-error diagnostics. When `true`, all errors are suppressed for files in this workspace, regardless of `pyrefly.toml` settings or preset. The status bar shows `Pyrefly (Errors Off)` and the hover explains the source. When `false` (the default), Pyrefly defers to the project's `pyrefly.toml` and any in-config `disable-type-errors-in-ide` flag. The project's committed config is authoritative.

There is no override that bypasses an in-config disable. If a project ships with `disable-type-errors-in-ide = true` and you want to see errors locally, remove the flag from your `pyrefly.toml`.

#### `python.pyrefly.displayTypeErrors` (deprecated)

**Type:** enum (`default`, `force-on`, `force-off`, `error-missing-imports`) &nbsp; **Default:** `"default"`

:::warning
Replaced by [`typeCheckingMode`](#pythonpyreflytypecheckingmode) and [`disableTypeErrors`](#pythonpyreflydisabletypeerrors). This setting still works for backwards compatibility but new configurations should use the replacements. When both legacy and new settings are present, the new settings take precedence.
:::

Legacy mapping onto the new model:

- `force-on` -> `typeCheckingMode = "default"`. No effect on `disableTypeErrors`.
- `force-off` -> `disableTypeErrors = true` (workspace kill switch). No effect on Pyrefly's behavior for files without a Pyrefly configuration.
- `default` resets both new settings to their unset values (`typeCheckingMode = "auto"`, `disableTypeErrors = false`). Use it to clear a previous `force-on` / `force-off` setting.
- `error-missing-imports` was removed in v0.64.0 and now behaves identically to `default`.

#### `python.pyrefly.diagnosticMode`

**Type:** enum (`openFilesOnly`, `workspace`) &nbsp; **Default:** `"openFilesOnly"`

Controls the scope of Pyrefly's diagnostic analysis. When set to `'openFilesOnly'`, diagnostics are only computed for files currently open in the editor. When set to `'workspace'`, Pyrefly publishes diagnostics for all files in a project once any file from that project is opened. Projects are identified through pyrefly config files (`pyrefly.toml` or `pyproject.toml` with `[tool.pyrefly]`) discovered by the normal upward config search. Files not covered by any explicit pyrefly config are not included.

#### `python.pyrefly.disableLanguageServices`

**Type:** boolean &nbsp; **Default:** `false`

If true, Pyrefly will not provide IDE services like completions, hover, definition, etc. Type errors are controlled separately via [`disableTypeErrors`](#pythonpyreflydisabletypeerrors) and [`typeCheckingMode`](#pythonpyreflytypecheckingmode). Set to `true` to keep type errors from Pyrefly unchanged but use VSCode's Python extension for everything else.

#### `python.pyrefly.disabledLanguageServices`

**Type:** object &nbsp; **Default:** `{}`

Granular toggle to disable individual language services. Set a service to `true` to disable it. For example, if you want go-to definition but not find-references.

Available services: `hover`, `documentSymbol`, `workspaceSymbol`, `inlayHint`, `completion`, `codeAction`, `definition`, `declaration`, `typeDefinition`, `references`, `documentHighlight`, `rename`, `codeLens`, `semanticTokens`, `signatureHelp`, `implementation`, `callHierarchy`.

Services not in this list can only be turned off wholesale via [`disableLanguageServices`](#pythonpyreflydisablelanguageservices).

:::note
`workspaceSymbol` and `callHierarchy` are accepted but not yet honored — setting them to `true` currently has no effect.
:::

#### `python.pyrefly.configPath`

**Type:** string &nbsp; **Default:** `""`

Path to a `pyrefly.toml` or `pyproject.toml` configuration file. When set, the LSP will use this config for all files in your workspace instead of the default Pyrefly config-finding logic wherever possible.

#### `python.pyrefly.streamDiagnostics`

**Type:** boolean &nbsp; **Default:** `true`

If true, Pyrefly streams diagnostics as they become available during recheck, providing incremental feedback. Set to `false` to only publish diagnostics after the full recheck completes.

#### `python.pyrefly.syncNotebooks`

**Type:** boolean &nbsp; **Default:** `true`

If true, Pyrefly will sync notebook documents with the language server. Set to `false` to disable notebook support.

#### `python.pyrefly.runnableCodeLens`

**Type:** boolean &nbsp; **Default:** `false`

Enable Pyrefly's Run/Test CodeLens actions for Python files.

#### `python.analysis.showHoverGoToLinks`

**Type:** boolean &nbsp; **Default:** `true`

Controls whether hover tooltips include "Go to definition" and "Go to type definition" navigation links. Set to `false` for cleaner tooltips with only type information.

#### `python.analysis.completeFunctionParens`

**Type:** boolean &nbsp; **Default:** `false`

Automatically insert parentheses when completing a function or method.

#### `python.analysis.autoImportCompletions`

**Type:** boolean &nbsp; **Default:** `true`

Controls whether completions include symbols that are not yet imported. When enabled, accepting such a completion also inserts the required import statement. Set to `false` to only complete symbols that are already in scope.

#### `pyrefly.lspPath`

**Type:** string &nbsp; **Default:** `""`

If your platform is not supported, you can build pyrefly from source and specify the binary path with this setting.

#### `pyrefly.lspArguments`

**Type:** array of strings &nbsp; **Default:** `["lsp"]`

Additional arguments passed to the binary at `pyrefly.lspPath`.

#### `pyrefly.trace.server`

**Type:** enum (`off`, `verbose`) &nbsp; **Default:** `"off"`

Set to `'verbose'` to enable LSP trace output in the console. Useful for debugging LSP communication issues.

#### `pyrefly.commentFoldingRanges`

**Type:** boolean &nbsp; **Default:** `false`

Controls whether comment section folding ranges are included in the editor. When `true`, comments following the pattern `# Section Name ----` (with 4+ trailing dashes) create collapsible regions, similar to R's code section convention.

#### `python.defaultInterpreterPath`

**Type:** string

This is a setting from the [Python extension](https://marketplace.visualstudio.com/items?itemName=ms-python.python). If the Python extension is installed, [selecting an interpreter](https://code.visualstudio.com/docs/python/environments) will override the interpreter and settings Pyrefly uses to type check your project, even if one is specified in your Pyrefly configuration. `python.defaultInterpreterPath` will override the default interpreter selected by VSCode for your workspace.

### LSP `initializationOptions`

When used with non-VSCode editors, the options above can also be configured by sending them via `initializationOptions` in the LSP [initialization](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#initialize) request.

The keys are the VSCode setting names with the leading `python.` stripped, so `python.pyrefly.typeCheckingMode` becomes `pyrefly.typeCheckingMode` and `python.analysis.importFormat` becomes `analysis.importFormat`. `analysis` is also accepted under `pyrefly` (`pyrefly.analysis.importFormat`) — the two are equivalent. Everything is optional; omitted keys keep their defaults.

Two exceptions: `commentFoldingRanges` sits at the top level rather than under `pyrefly`, and `pyrefly.lspPath` / `pyrefly.lspArguments` / `pyrefly.trace.server` have no `initializationOptions` equivalent at all — they tell the VSCode extension how to launch the server, which your client already does itself.

Below is an example showing every supported key at its default value:
```json
{
  "pythonPath": "/usr/bin/python3",
  "commentFoldingRanges": false,
  "analysis": {
    "diagnosticMode": "openFilesOnly",
    "importFormat": "absolute",
    "completeFunctionParens": false,
    "autoImportCompletions": true,
    "showHoverGoToLinks": true,
    "inlayHintDebounceMs": 0,
    "inlayHints": {
      "callArgumentNames": "off",
      "functionReturnTypes": true,
      "pytestParameters": false,
      "variableTypes": true
    }
  },
  "pyrefly": {
    "typeCheckingMode": "auto",
    "disableTypeErrors": false,
    "displayTypeErrors": "default",
    "typeErrorDisplayStatusVersion": "v1",
    "disableLanguageServices": false,
    "diagnosticMode": "openFilesOnly",
    "extraSearchPaths": [],
    "extraProjectExcludes": [],
    "configPath": "",
    "streamDiagnostics": true,
    "syncNotebooks": true,
    "runnableCodeLens": false,
    "disabledLanguageServices": {
      "hover": false,
      "documentSymbol": false,
      "workspaceSymbol": false,
      "inlayHint": false,
      "completion": false,
      "codeAction": false,
      "definition": false,
      "declaration": false,
      "typeDefinition": false,
      "references": false,
      "documentHighlight": false,
      "rename": false,
      "codeLens": false,
      "semanticTokens": false,
      "signatureHelp": false,
      "implementation": false,
      "callHierarchy": false
    }
  }
}
```

#### Keys not covered above

Every other key means exactly what the same-named [VSCode setting](#vscode-extension-settings) means. These ones aren't in that list — either because they have no VSCode counterpart, or because they're inherited from Pylance's settings rather than being Pyrefly's own.

##### `pythonPath`

**Type:** string

Absolute path to the Python interpreter whose environment (version, platform, `site-packages`) Pyrefly should use. Equivalent to [`python-interpreter-path`](../configuration#python-interpreter-path) in a config file, and ignored for files whose resolved config specifies an interpreter of its own.

##### `pyrefly.extraSearchPaths`

**Type:** array of strings &nbsp; **Default:** `[]`

Extra directories to resolve imports from, appended to the [`search-path`](../configuration#search-path) of whatever config Pyrefly resolves for a file. Named to match Pyrefly's own `search-path`, and prefixed `extra` because the entries are added to that path rather than replacing it.

##### `pyrefly.extraPaths` (deprecated)

**Type:** array of strings &nbsp; **Default:** `[]`

:::warning
Renamed to [`extraSearchPaths`](#pyreflyextrasearchpaths). Still accepted for backwards compatibility, and for clients already forwarding Pylance's similarly-named `python.analysis.extraPaths`.
:::

##### `pyrefly.extraProjectExcludes`

**Type:** array of strings &nbsp; **Default:** `[]`

Globs to exclude from the project, appended to the [`project-excludes`](../configuration#project-excludes) of whatever config Pyrefly resolves for a file. Files matching them are not type checked: no diagnostics are published for them, and they are skipped when [`diagnosticMode`](#pythonpyreflydiagnosticmode) is `workspace`.

Use this to map an editor's own notion of excluded directories (for example PyCharm's "Excluded" content roots) onto Pyrefly without writing a `pyrefly.toml`. Relative globs are resolved against the workspace folder the setting is scoped to; patterns use `/` as the separator on every platform.

Because the globs are appended, this can only ever remove files from a project — it cannot re-include a file the project's own `project-excludes` already excluded.

:::note
Excluded files are still available for import resolution: an excluded module that a checked file imports is read and analyzed, it just doesn't report its own errors. Language services (hover, go-to-definition, completions) also keep working inside excluded files. To stop resolving imports out of a directory entirely, leave it off the [`search-path`](../configuration#search-path).
:::

##### `pyrefly.typeErrorDisplayStatusVersion`

**Type:** enum (`v1`, `v2`) &nbsp; **Default:** `"v1"`

Wire shape the server should use when answering [`pyrefly/textDocument/typeErrorDisplayStatus`](#custom-request-pyreflytextdocumenttypeerrordisplaystatus). See that section for the two shapes and the version-negotiation rules.

##### `analysis.diagnosticMode`

**Type:** enum (`openFilesOnly`, `workspace`) &nbsp; **Default:** `"openFilesOnly"`

Same meaning as [`pyrefly.diagnosticMode`](#pythonpyreflydiagnosticmode), and read only as a fallback when that is unset. Exists so that a client already forwarding Pylance's `python.analysis.diagnosticMode` gets the expected behavior for free.

##### `analysis.importFormat`

**Type:** enum (`absolute`, `relative`) &nbsp; **Default:** `"absolute"`

Whether the import statements Pyrefly inserts — for auto-import completions and the move-symbol / convert-module code actions — are written as absolute or relative imports. Mirrors Pylance's `python.analysis.importFormat`.

##### `analysis.inlayHintDebounceMs`

**Type:** number &nbsp; **Default:** `0`

Debounce window in milliseconds for inlay hint requests. When the document was edited within this window, the request is deferred until editing pauses, which stops hint widths from jittering on every keystroke. `0` disables debouncing.

##### `analysis.inlayHints`

**Type:** object

Which inlay hints to produce:

- `callArgumentNames` (enum `all`, `off`, `partial`, default `"off"`): show parameter names on positional arguments at call sites. `all` and `partial` currently behave identically; the enum matches Pylance's `python.analysis.inlayHints.callArgumentNames`.
- `functionReturnTypes` (boolean, default `true`): show inferred return types on unannotated functions.
- `pytestParameters` (boolean, default `false`): accepted for Pylance compatibility, currently has no effect.
- `variableTypes` (boolean, default `true`): show inferred types on unannotated assignments.

#### Scoping and `workspace/configuration`

`initializationOptions` are applied twice: once to a catch-all default scope covering every file on the system, and once per workspace folder listed in the `initialize` request. Relative `extraProjectExcludes` globs are therefore rooted at each workspace folder, and files outside every folder fall back to the default scope, where only absolute globs can match.

If the client advertises the `workspace.configuration` capability, Pyrefly additionally requests the `python` section for each workspace folder (plus a folder-less request for the default scope) and applies the responses on top of `initializationOptions`, both at startup and on every `workspace/didChangeConfiguration`. A client that advertises the capability should answer with the same settings it sent in `initializationOptions`; returning a `pyrefly` object that omits a key resets that key to its default.

### Custom request: `pyrefly/textDocument/typeErrorDisplayStatus`

Third-party integrators can ask the server about Pyrefly's current
type-checking state for a given file via the custom request
`pyrefly/textDocument/typeErrorDisplayStatus`. The wire shape is
versioned via `initializationOptions.pyrefly.typeErrorDisplayStatusVersion`:

- `"v1"` (legacy default): the server returns a bare JSON string from
  the original `TypeErrorDisplayStatus` enum
  (`enabled-in-config-file`, `disabled-in-ide-config`, `no-config-file`,
  etc.). Every historical client can decode this shape. A missing or
  unspecified version also resolves to `v1` so older clients keep
  working unchanged.
- `"v2"`: the server returns an object:
  ```json
  {
    "version": "v2",
    "label": "Basic" | "Legacy" | "Default" | "Errors Off" | null,
    "tooltip": "markdown string",
    "docsUrl": "https://pyrefly.org/...",
    "pyreflyVersion": "1.2.3" | null,
    "buildSystem": "building" | "ready" | "error: <message>" | null
  }
  ```
  `Basic` / `Legacy` / `Default` are emitted when Pyrefly synthesized
  a config (no `pyrefly.toml` was found) and tell the user which
  preset is active. `Errors Off` is emitted whenever diagnostics are
  suppressed, either by the workspace `disableTypeErrors` kill switch
  or by in-config `disable-type-errors-in-ide`. `null` is emitted for
  everything else (project has a real `pyrefly.toml`, or the user
  explicitly set `typeCheckingMode`). In that case the client should
  render plain `Pyrefly` with no parenthetical. The Pyrefly VS Code
  extension uses V2 to render the status-bar parenthetical (e.g.
  `Pyrefly (Basic)` or `Pyrefly (Errors Off)`).

  `buildSystem` reports the state of the most recent source-database
  query for projects configured with a `[build-system]`. It is `null`
  for projects without one, which is why clients should render it only
  when present rather than assuming a build system exists.

Clients should dispatch on response shape (`typeof resp === 'string'`
for V1, `resp.version` for V2+) so they can transparently support
servers older than the version they declared.

If a client opts into a version the server doesn't recognize (e.g. a
future `v3` against a server that only knows up to `v2`), the server
clamps to the latest version it can produce (`v2` in that example).
The richer shape is the closest the server can offer to what the
client asked for. A fallback to `v1` would silently strip features
the client explicitly requested. Clients should still defensively
dispatch on `resp.version` so they can recognize when the server has
clamped them down.

### Custom notification: `pyrefly/typeErrorDisplayStatusChanged`

`typeErrorDisplayStatus` is a request, so a client only learns about
changes when it asks. Most of the response is static for a given file,
but `buildSystem` changes on its own as the build system runs. To keep
clients from showing a stale build state, the server can push a
notification telling them to re-request.

Opt in by setting
`initializationOptions.pyrefly.pushTypeErrorDisplayStatus` to `true`
alongside `typeErrorDisplayStatusVersion: "v2"`. The server then sends
`pyrefly/typeErrorDisplayStatusChanged` whenever the build-system state
changes. It defaults to `false` so clients that predate the notification
never receive one they would only log as unhandled.

The notification carries no parameters. The status is derived per
document and only the client knows which document it is displaying, so
the correct reaction is to re-issue `typeErrorDisplayStatus` for the
current file. Clients should debounce: a single rebuild sends at least a
`building` and a `ready` transition.

### Jetbrains / Pycharm
PyCharm users can enable native Pyrefly support in the settings:
1. Go to **Python | Tools | Pyrefly** in the Settings dialog.
2. Select the **Enable** checkbox.
3. In the Execution mode setting, select how PyCharm should search for the executable:

    **Interpreter** mode: PyCharm searches for an executable installed in your interpreter. To install the Pyrefly package for the selected interpreter, click *Install Pyrefly*.

    **Path** mode: PyCharm searches for an executable in `$PATH`. If the executable is not found, you can specify the path by clicking the  Browse... icon.

4. Select which options should be enabled.

For more information, refer to [PyCharm documentation](https://www.jetbrains.com/help/pycharm/lsp-tools.html#pyrefly).

### Neovim

Pyrefly supports native Neovim support through `lspconfig` on Neovim 0.11+. Install and setup Pyrefly using the settings below.

The recommended way to set up Pyrefly in **Neovim 0.11+** is:
1. Install or update the [`neovim/nvim-lspconfig`](https://github.com/neovim/nvim-lspconfig), [`mason-org/mason.nvim`](https://github.com/mason-org/mason.nvim), and [`mason-org/mason-lspconfig.nvim`](https://github.com/mason-org/mason-lspconfig.nvim) plugins with your plugin manager of choice.
2. Add the following to your Neovim `init.lua`:
```lua
require("mason").setup()
require("mason-lspconfig").setup()
```
3. In Neovim, run `:MasonInstall pyrefly` or add `pyrefly` to your `ensure_installed` options:
```lua
require("mason-lspconfig").setup {
  ensure_installed = { "pyrefly" },
}
```

### Vim/Neovim + coc.nvim

Ensure the pyrefly is on `$PATH`, add following snippet to your `coc-settings.json`:

```json
"languageserver": {
  "pyrefly": {
    "command": "pyrefly",
    "args": ["lsp"],
    "filetypes": ["python"],
    "rootPatterns": ["pyrefly.toml", "pyproject.toml", ".git"],
  }
},
```

:::tip
For projects without a Pyrefly configuration, Pyrefly migrates a nearby mypy/pyright configuration in memory or falls back to the `basic` preset (a small set of high-confidence diagnostics). To switch to a stricter preset for files not covered by a `pyrefly.toml`, add the following `initializationOptions`:

```json
"languageserver": {
  "pyrefly": {
    "command": "pyrefly",
    "args": ["lsp"],
    "filetypes": ["python"],
    "rootPatterns": ["pyrefly.toml", "pyproject.toml", ".git"],
    "initializationOptions": {
      "pyrefly": {
        "typeCheckingMode": "default"
      }
    }
  }
}
```

Available values: `"auto"` (the default; migrates a nearby mypy/pyright config in memory or falls back to `basic`), `"off"`, `"basic"`, `"legacy"`, `"default"`, `"strict"`, `"all"`. To suppress all diagnostics in this workspace regardless of preset, use `"disableTypeErrors": true` instead.
:::

### Emacs

There are several emacs packages that implement the language server protocol; the `eglot` package
is built into recent versions of emacs. You can tell `eglot` to use `pyrefly` (which we assume
is on your `$PATH`) with the following configuration:
```
(add-to-list 'eglot-server-programs
  `((python-ts-mode python-mode) . ("pyrefly" "lsp")))
```

If you are using `use-package`, this command would run inside of the `:config` block; a minimal
example would look like this:
```
(use-package eglot
  :ensure t
  :hook ((python-mode python-ts-mode) . eglot-ensure)
  :config
  (add-to-list 'eglot-server-programs
    `((python-ts-mode python-mode) . ("pyrefly" "lsp"))))
```

### Jupyter Lab

Pyrefly may be used in Jupyter Lab through the [jupyterlab-lsp](https://jupyterlab-lsp.readthedocs.io/en/latest/Installation.html) extension.
Once the extension is installed, Pyrefly will appear on the list of automatically-detected language servers.

:::tip
Unlike in VS Code, autocomplete in Jupyter Lab is not automatically-triggered as you type. To enable this, enable Code Completion & Continuous Completions in the Jupyter Lab Settings.

Out of the box, Jupyter Lab's go-to-definition will not navigate to dependencies outside of your project. To enable this behavior:
1. Go to your project directory and run `ln -s / .lsp_symlink`
2. When launching Jupyter Lab, use `jupyter lab --ContentsManager.allow_hidden=True`
:::
