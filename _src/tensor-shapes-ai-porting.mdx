# Agent Skill for Tensor Shape Porting

Pyrefly includes a skill for [Claude Code](https://docs.anthropic.com/en/docs/claude-code/overview)
that can automatically port PyTorch models to use tensor shape annotations. The
skill runs a structured, multi-step workflow — auditing ops, inventorying
parameters, probing shapes with `reveal_type`, containing tracking boundaries,
and verifying the result — that produces an annotated model and a report of
what could not be tracked.

## Where the skill lives

The skill is a directory in the Pyrefly source tree:

```
tensor-shapes/skills/add-shape-types-to-torch-model/
```

You can either copy the skill into your configuration and use a
slash command like `/add-shape-types-to-torch-model` to invoke it, or you
can just point your agent at the skill file and ask it to follow the steps.


## What should the agent do?

The skill will:

1. **Resolve setup** — choose the check command, confirm that Pyrefly sees the
   shape-aware stubs and a real `torch` installation, and decide whether stub
   changes are in scope. For your own model, it leaves shared stubs unchanged
   by default and reports gaps.
2. **Audit ops** — classify every module, `torch`/`F.` function, and Tensor
   method the model uses as tracked by a stub signature, a shape DSL rule, or a
   special handler, or as a gradual boundary. This is a diagnostic pass, not a
   blocker.
3. **Inventory the original** — list every class, method, and function, noting
   which constructor parameters are `Int` vs `int`.
4. **Port each module in dependency order** — for each module, inventory
   parameters, type the constructor, probe the forward with `reveal_type`,
   diagnose each bare result and contain it with annotation-only repairs or a
   narrow `cast`, write the forward with `assert_type` checkpoints, and run a
   post-module check.
5. **Verify** — run `pyrefly check` and `verify_port.sh`, audit bare
   `assert_type` calls, compare against the style guide, and produce a
   completion report.

The skill preserves runtime behavior. It does not restructure containers,
loops, or factories to improve tracking; it reports such rewrites as
suggestions for you to approve separately.

## The iterate-and-reflect loop

A first pass typically leaves some gaps — bridge dimensions, optional
dimensions, and parameterized configs — that benefit from another pass where
the AI reflects on what it missed.

The workflow:

1. **First pass.** Invoke the skill. Review the completion report, paying
   attention to remaining gradual boundaries, bare `assert_type` calls, and
   any `type: ignore` comments.
2. **Reflect.** Ask the AI to re-read the skill file and compare what it did
   against what the skill prescribes. A prompt like:

   ```
   Re-read the add-shape-types-to-torch-model skill and reflect on the port you
   just produced. What did you miss? What could be improved?
   ```

   This typically surfaces missed annotation-only repairs — cases where the
   AI accepted a bare `Tensor` or a cast without checking the exact stub,
   shape rule, or special handler, as Step 4 of the skill prescribes.

3. **Second pass.** Ask it to fix the issues it identified. This usually
   converges: bare results drop and shaped coverage improves.

Repeat the reflection pass until remaining gaps are intentional and documented.
Models with dynamic patterns such as `nn.Sequential(*list)`, conditional
branching, or late-initialized buffers may need additional review.

## Reading the output

The skill runs `verify_port.sh`, which prints a summary with these counts.
They come from line-oriented pattern matching, so treat them as hints;
`pyrefly check` is the source of truth.

| Count | What it means |
|--------|--------------|
| **`type: ignore`** | `type: ignore` comments. Lower is better. Each should name its cause (algebraic gap, conditional equality, stub gap) and the exact `pyrefly:<code>`. |
| **`bare Tensor (sig)`** | Bare `Tensor` in function signatures. Should be 0 unless the rank is genuinely unknown. |
| **`bare Tensor (var)`** | Bare `Tensor` in local variable annotations. Lower is better. |
| **`assert_type`** | `assert_type` calls, split into shaped ones with full shapes (e.g., `Tensor[[B, D]]`) and bare ones (`assert_type(x, Tensor)`), which mark tracking gaps. Each bare one should have a root-cause comment. |
| **`smoke tests`** | `test_` functions in the file. Required only for ports contributed to the example corpus. |

A good port has precise module signatures, few bare `assert_type` calls, and
every remaining gradual boundary traced to a documented root cause.

## When to intervene

The AI workflow handles most patterns automatically, but some decisions require
domain knowledge:

- **Bridge dims.** When an untracked section (e.g., a feature extractor built
  with `nn.Sequential(*list)`) connects to a tracked downstream module, you may
  need to decide which dimension to promote to a class type parameter.
- **Missing stubs.** If the model uses ops that the shape-aware stubs don't
  cover, decide whether improving the stubs is in scope; otherwise the skill
  contains the gap at a typed boundary and reports it.
- **Architectural choices.** When the skill suggests a rewrite that would
  improve tracking (e.g., separating the first iteration of a loop or replacing
  a dynamic container), domain knowledge about the model's invariants decides
  whether the change is worth making.
- **Config parameterization.** Deciding which config fields should become `Int`
  type parameters (and which modules extract which parameters) is often a design
  decision about the model's API, so the skill makes a config generic only when
  you agree to that narrower static API.
